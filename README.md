# Модульная разработка solution.ipynb

`solution.ipynb` — сохранённый рабочий оригинал. Его неизменяемая резервная копия — `solution.original.ipynb`. Сборка записывается отдельно в `tmp/solution.generated.ipynb`; ни одна команда ниже не заменяет оригиналы

## Структура

```text
notebooks/
  00_preliminary.ipynb      # 0: загрузка, смысловые типы, интерпретации
  01_problem.ipynb          # 1: постановка задачи
  02_overview.ipynb         # 2.1: общий обзор
  03_data_quality.ipynb     # 2.2: проверки и промежуточная очистка
  04_univariate.ipynb       # 2.3: одномерный анализ и выводы
  05_split.ipynb            # 3: train / validation / test
  06_multivariate.ipynb     # 4: гипотезы, ассоциации, матрица и выводы
src/
  associations.py          # три существующие функции ассоциаций
  visualization.py         # существующая функция тепловой матрицы
scripts/
  build.py                 # сборка с встраиванием функций
  validate.py              # структурная и исполняемая проверка
  capture_runtime.py       # только проверочный сбор результатов
notebook_manifest.json     # порядок разделов и контрольная сумма оригинала
tmp/                      # временные файлы, целиком вне Git
  solution.generated.ipynb # автономная сборка
  validation_report.md    # отчёт последней проверки
  validation_artifacts/   # выполненные копии, снимки и status.json
  python-cache/           # кэш Python
  runs/                   # временные каталоги запуска ядер
```

## Редактирование

Открывайте разделы в порядке из `notebook_manifest.json` и выполняйте их в **одном общем Jupyter kernel**. В VS Code выберите для разделов один и тот же уже запущенный kernel; одинаковый интерпретатор сам по себе ещё не означает общий kernel

Первая служебная ячейка каждого раздела устанавливает рабочий каталог `sem2/task`, даже если раздел открыт из `notebooks/`. Выполняйте её перед остальными ячейками. Она не попадает в итоговую сборку

Разделы являются полноценными `.ipynb`, но поздние разделы зависят от состояния предыдущих. Они намеренно не загружают и не очищают данные заново

Редактируйте Markdown и аналитические ячейки в `notebooks/`, вынесенные определения — в `src/`. После изменения `.py` повторно выполните ячейку его загрузки в разделе 06. Эта ячейка использует `exec(compile(...), globals())`, чтобы сохранить исходное разрешение notebook globals и не менять сигнатуры функций. Эти файлы предназначены для notebook namespace, а не для обычного `import src...`

Не удаляйте `metadata.modular` у служебных ячеек и загрузчиков. Сборщик использует эти метаданные для исключения bootstrap и замены загрузчиков исходными `def` ровно в их прежних позициях. Изменённые функции подхватываются при следующей сборке без изменения сборщика

## Сборка одной командой

Из корня этого каталога:

```bash
../../.venv/bin/python scripts/build.py
```

Результат: `tmp/solution.generated.ipynb`. Сборщик использует `nbformat`, сохраняет Markdown, формулы, встроенную картинку, порядок ячеек, метаданные и существующие outputs. Встроенные функции идут в исходном порядке, локальные проектные импорты не требуются. Сохранившиеся outputs могут быть устаревшими после ваших правок — сборка сама не исполняет анализ

Сборка детерминирована. `--output` позволяет задать другой файл, но перезапись оригиналов и исходников запрещена

## Проверка одной командой

После сборки:

```bash
../../.venv/bin/python scripts/validate.py
```

Проверка использует текущий `sys.executable` для новых Jupyter-ядер и выполняет:

1. Контроль SHA-256 обоих оригиналов
2. Сравнение текста, вложений, метаданных и полного упорядоченного Python AST
3. Проверку, что generated соответствует актуальным модульным исходникам
4. Запуск оригинала и generated в разных временных каталогах с `data/`, без `src/`, `notebooks/`, `scripts/` и проектного `PYTHONPATH`
5. Запуск модульных разделов в одном чистом kernel
6. Сравнение отображённых таблиц, конечных объектов данных и данных графиков с `rtol=1e-9`, `atol=1e-11`

Результат: `tmp/validation_report.md`, подробности в `tmp/validation_artifacts/`. Код выхода 0 означает успешную проверку; 1 — расхождение, ошибку или невозможность обязательной проверки. Для ячеек можно увеличить тайм-аут: `--timeout 300`

В ограниченной среде Jupyter могут понадобиться разрешения на локальные порты. Ошибка запуска ядра отмечается как недоступная проверка, а не как успешная

Для воспроизводимости в проверочном окружении одинаково задаются seed=42 и PYTHONHASHSEED=0. Настройки аналитических ячеек не меняются. HTML UUID не сравниваются, вместо них сравниваются данные таблиц. PNG побайтово не сравниваются — проверяются данные и свойства графиков

Отчёт доказывает совпадение текущей версии с резервной копией на текущем датасете. После содержательных изменений ожидается расхождение с резервной копией: не заменяйте её автоматически, сначала рассмотрите результат и осознанно определите новый эталон

## Автономное использование

При открытии сборки из `tmp/` установите рабочий каталог kernel в корень проекта (`%cd ..` из `tmp/`), чтобы относительный путь к данным остался прежним

Для `tmp/solution.generated.ipynb` нужны только установленные библиотеки и `data/credit_risk_dataset.csv` относительно рабочего каталога. `src/`, `notebooks/` и `scripts/` для его выполнения не нужны

Используйте Python-окружение проекта: pandas, NumPy, SciPy, scikit-learn, matplotlib, seaborn, IPython, nbformat, nbclient, ipykernel и jupyter_client. Версии проверенного окружения записаны в `tmp/validation_artifacts/environment.json`

## Тесты инструментов

```bash
../../.venv/bin/python -X pycache_prefix=tmp/python-cache -m unittest discover -s tests -v
```

Тесты проверяют вставку обновлённых модулей, порядок зависимостей, вложения, защиту оригиналов, ошибочные placeholders, дубли определений, структурные расхождения и сравнение численных результатов. Полная проверка исполнения запускается отдельно командой `validate.py`

Временные результаты находятся в `tmp/`, который исключён из Git. Окружение `.venv/` и локальные настройки редактора остаются в стандартных местах. `sandbox.ipynb` и исходный скриншот сохранены как пользовательские материалы
