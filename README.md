# Курсовая: оценка кредитного риска

Исходники определяют предметный анализ, инструменты собирают и исполняют его. Итоговая сборка находится в `build/`, временные материалы — в `tmp/`

## Окружение

Все команды выполняются из корня курсовой. Используйте Python 3.13+ с зависимостями из `pyproject.toml`. `requirements.lock` — точный снимок установленных версий проверенного окружения, включая транзитивные зависимости; это не универсальный кроссплатформенный lock с хешами

При создании окружения:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
source .venv/bin/activate
```

Дальше `python` означает интерпретатор этого окружения.

Статистика проекта: `python -m tooling.project_stats`. Команда выводит и сохраняет в `project.stats.txt` в корне пять показателей: суммарный размер файлов (включая датасет), число файлов, число notebooks, строки кода и строки текста. Учитываются файлы Git и новые файлы, не исключённые через `.gitignore`. Код считается в `.py` и кодовых ячейках notebooks; текст — в `.md`, `.txt`, Markdown- и raw-ячейках. Пустые строки и комментарии учитываются, результаты выполнения ячеек в число строк не входят. Размер — сумма размеров файлов, без служебных данных Git. Оба файла статистики исключены из подсчёта. `project.stats.txt` и `build/solution.stats.txt` версионируются в Git; остальные результаты сборки исключены.

## Сборка

```bash
python -m tooling.build.builder
# build/solution.ipynb
```

Сборщик создаёт автономный notebook и копирует `dataset/credit_risk_dataset.csv` рядом с ним в `build/` (при `--output` — в папку указанного файла). Другие форматы ещё не реализованы. `--output /путь/файл.ipynb` позволяет задать другой выход, но запрещает перезапись исходников и данных

Рядом со сборкой создаётся `solution.stats.txt`: размер notebook, число ячеек, строки кода, строки текста, число слов в текстовых ячейках, минимум и максимум строк в кодовой ячейке. Пустые строки и комментарии учитываются. Команда выполнения обновляет эти семь показателей после сохранения результатов.

Манифест — `project.json`. Сборщик сохраняет Markdown, формулы, вложения и порядок операций, встраивает Python-код на место объявленных загрузчиков. Сборка без запуска может содержать устаревшие outputs. Для готового файла с заново выполненными расчётами:

```bash
python -m tooling.execution.runner
# build/solution.ipynb — выполненный notebook
```

Команда сама собирает notebook, копирует CSV рядом с результатом и выполняет его в чистом kernel из папки сборки; после ошибки результат не перезаписывается. Требуются локальные порты Jupyter. При сдаче приложите `credit_risk_dataset.csv` рядом с notebook.

## Интерактивная разработка

Начальная точка — `src/index.ipynb`: оглавление семи этапов и их включение по порядку. У больших этапов есть собственный `index.ipynb`, который включает подэтапы. Можно открывать конкретные файлы, выполняя предыдущие этапы в одном общем kernel; одинаковый интерпретатор не означает один процесс

В начале каждого файла этапа/подэтапа указаны «Входы», «Выходы», «Что делаем». Служебная ячейка находит `project.json` и устанавливает cwd в корень курсовой. При интерактивном выполнении включения показывают текст подэтапов и выполняют код в том же namespace

Небольшие Python-блоки хранятся прямо в кодовых ячейках рядом с пояснениями. Крупные блоки находятся в `_code/` рядом с включающим notebook. После правки `.py` повторно выполните ячейку его загрузки. Служебные `metadata.modular` задают вставку исходников и не должны удаляться. Итоговый notebook содержит обычный код без локальных загрузчиков

Служебные блоки помечаются тегом ячейки `dev-only` и видимой пометкой `# dev-only:` в коде или `dev-only` в Markdown. Обычные ячейки с этим тегом исключаются из сборки. Ячейки включения notebook и загрузки `.py` также помечены `dev-only`: их служебный код заменяется содержимым подключённых файлов. Метка загрузчика в итоговый notebook не переносится. Не помечайте этим тегом аналитический код, который должен остаться в результате.

В начале готового notebook указаны требования к Python, команда установки зависимостей из `pyproject.toml` и инструкция по размещению данных. Ячейка установки выполняется перед импортами: имена библиотек берутся из `pyproject.toml`, но версии не закрепляются и `--upgrade` не используется. IPython предоставляет ядро Jupyter/Colab, поэтому команда его не устанавливает. Точные версии в `pyproject.toml` остаются для локального окружения. Результаты на других версиях библиотек могут отличаться. Положите `credit_risk_dataset.csv` рядом с notebook и запускайте его из этой папки. В Colab загрузите CSV в рабочую папку через панель файлов. Сборщик уже помещает CSV рядом с итоговым notebook; готовый notebook читает только этот файл. Автоматического скачивания данных нет.

## Содержание завершённой работы

Все семь этапов заполнены. Общий EDA и фиксированная очистка исторически сделаны до случайного стратифицированного разбиения 70/15/15. Дополнительный анализ — только train. Pipeline обучает медианы, моду, масштабирование и кодирование только на train. Loan grade использует порядок A–G, бинарные признаки считаются номинальными. Сравниваются Dummy, логистическая регрессия, лес и гистограммный бустинг; модель выбирается по validation AP, порог — по validation F2. После фиксации test используется для итоговых метрик, bootstrap-интервалов и графиков, без донастройки.

Окончательная таблица выводов находится в этапе 7. Это учебный эксперимент на одном Kaggle-разбиении; реальные условия кредитования, внешняя валидация и мониторинг описаны как ограничения и дальнейшая работа. Сервис не развёртывается. Итоговый notebook содержит код и результаты, проектные Python-импорты для его запуска не нужны.

Описания столбцов и наши пояснения в этапе 1 хранятся в простых HTML-таблицах Markdown-ячеек. В Python остаются загрузка данных, вычисление диапазонов и определение типов признаков.

## Таблица выводов

В начале этапа 3 `conclusions = empty_findings()` создаёт пустую общую таблицу Pandas. После подэтапов `update_findings` добавляет записи `(id, вывод, решение)` и принимает список `remove` для закрытых записей. Постоянный id позволяет уточнить вывод без дублирования актуальной версии

`Метка` принимает `new`, `removed` или пустую строку. `findings_view(conclusions)` показывает всю таблицу, `findings_view(conclusions, only_new=True)` — только новые выводы. Новые строки выделяются зелёным и знаком «+», удаляемые — красным и знаком «−». На следующем обновлении удаляемые строки исчезают, а предыдущие новые становятся обычными. В коде метки хранятся отдельно от текста

Маленькие обновления находятся прямо после соответствующего анализа. Общие функции обработки и оформления — в соседнем `_code/findings.py`.

## Пошаговое выполнение анализа

Этап 3 отдельно включает `04_hypothesis_checks.ipynb` с проверкой гипотез и `05_model_specification.ipynb` с выбором спецификаций

В этапе 4 обработка показана по шагам: состав признаков и выборки, числовые признаки, номинальные категории, грейд, общая цепочка. Короткие определения преобразований находятся прямо рядом с пояснениями в notebook. Проверка новых заявок вынесена в `_code/prepare_applications.py` и подключается перед локальным прогнозом

Проверки гипотез, обучение и итоговая оценка также разделены на пояснения и соответствующие вычисления. Крупные блоки построения диагностических графиков и итоговой таблицы выводов остаются в соседней `_code/`
