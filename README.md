# Курсовая: оценка кредитного риска

Исходники определяют предметный анализ, инструменты собирают и исполняют его, тесты задают ожидаемое поведение. Итоговая сборка находится в `dist/`, проверочная сборка, отчёты проверок и временные материалы — в `tmp/`

## Окружение

Все команды выполняются из корня курсовой. Используйте Python 3.13+ с зависимостями из `pyproject.toml`. `requirements.lock` — точный снимок установленных версий проверенного окружения, включая транзитивные зависимости; это не универсальный кроссплатформенный lock с хешами

При создании окружения:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
source .venv/bin/activate
```

Дальше `python` означает интерпретатор этого окружения. В текущей рабочей сессии проверка также выполняется существующим окружением `../../.venv/bin/python`; переустанавливать его не требуется

## Сборка

```bash
python -m tooling.build.builder
# dist/solution.ipynb

python -m tooling.build.builder --target validation
# tmp/build/solution.ipynb
```

Пока обе цели дают одинаковый автономный notebook; различаются назначением и путём результата. Другие форматы ещё не реализованы. `--output /путь/файл.ipynb` позволяет задать другой выход, но запрещает перезапись исходников, данных и эталонов

Рядом с каждой записанной сборкой создаётся `solution.stats.html` (при другом имени notebook — `<имя>.stats.html`). Это автономный HTML-отчёт с таблицами: основные сведения о сборке, объём текста и кода, сложность Python и частотность слов. Размеры больше 0,1 МБ показываются в МБ, меньшие — в КБ. Команда выполнения обновляет отчёт после сохранения результатов

Подробности подсчёта и пять самых сложных функций свёрнуты. В частотной таблице сначала показаны 30 слов, доступны поиск и переключение на полный список. Учитываются Markdown и текстовые выводы, без кода, формул, адресов и чисел; регистр не различается, формы слов не объединяются. Повторные показы таблиц учитываются каждый раз

Манифест — `config/build/project.json`. Сборщик сохраняет Markdown, формулы, вложения и порядок операций, встраивает Python-код на место объявленных загрузчиков. Сборка без запуска может содержать устаревшие outputs. Для готового файла с заново выполненными расчётами:

```bash
python -m tooling.execution.runner --target submission
# dist/solution.ipynb — выполненный notebook
```

Команда сама собирает notebook и выполняет его в чистом kernel; после ошибки результат не перезаписывается. Требуются локальные порты Jupyter. При сдаче приложите dataset/ или сохраните её рядом с notebook.

## Интерактивная разработка

Начальная точка — `src/notebooks/index.ipynb`: оглавление семи этапов и их включение по порядку. У больших этапов есть собственный `index.ipynb`, который включает подэтапы. Можно открывать конкретные файлы, выполняя предыдущие этапы в одном общем kernel; одинаковый интерпретатор не означает один процесс

В начале каждого файла этапа/подэтапа указаны «Входы», «Выходы», «Что делаем». Служебная ячейка находит `config/build/project.json` и устанавливает cwd в корень курсовой. При интерактивном выполнении включения показывают текст подэтапов и выполняют код в том же namespace

Небольшие Python-блоки хранятся прямо в кодовых ячейках рядом с пояснениями. Крупные блоки находятся в `_code/` рядом с включающим notebook. После правки `.py` повторно выполните ячейку его загрузки. Служебные `metadata.modular` задают вставку исходников и не должны удаляться. Итоговый notebook содержит обычный код без локальных загрузчиков

Служебные блоки помечаются тегом ячейки `dev-only` и видимой пометкой `# dev-only:` в коде или `dev-only` в Markdown. Обычные ячейки с этим тегом исключаются из сборки. Ячейки включения notebook и загрузки `.py` также помечены `dev-only`: их служебный код заменяется содержимым подключённых файлов. Метка загрузчика в итоговый notebook не переносится. Не помечайте этим тегом аналитический код, который должен остаться в результате. `sandbox.ipynb` целиком относится к `dev-only`.

Для запуска готового notebook нужны только Python-библиотеки и `dataset/credit_risk_dataset.csv` относительно cwd. Если открыли файл из `dist/`, установите cwd в корень проекта либо скопируйте notebook и dataset/ в отдельный каталог

## Проверки

```bash
python -m tooling.testing.runner                 # быстрые unit-тесты
python -m tooling.testing.runner --suite integration
python -m tooling.testing.runner --suite regression  # три чистых kernel
python -m tooling.testing.runner --suite full        # всё
```

Регрессионная проверка сама создаёт свежую сборку validation. Неизменённый EDA проверяется отдельно: контрольные суммы эталонов, происхождение 68 ячеек, текст с явно разрешёнными редакторскими правками, упорядоченный AST, результаты выполнения original / legacy. Затем целиком сравниваются свежая автономная сборка и модульный notebook в разных чистых ядрах. Новое обучение не сравнивается со старым эталоном, в котором его нет. Дополнительно проверяются контракты разбиения, матрицы, выбора модели и порога, итоговых test-метрик.

Standalone исполняется в изолированной папке только с данными. Старому эталону предоставляется ссылка data → dataset. Для сравнения используются таблицы, итоговые объекты и данные графиков (`rtol=1e-9`, `atol=1e-11`); UUID Styler и байты PNG не сравниваются. Всего четыре чистых kernel.
Результаты: `tmp/reports/validation_report.md`, подробности и `status.json` — в `tmp/reports/validation/`. Код выхода 0 означает успех; 1 — ошибку, расхождение или недоступность обязательной проверки. Jupyter нужны локальные порты

Исходные параметры EDA не менялись. Графики дохода показываются последовательно: обычная шкала, вывод по ней, затем логарифмическая. Это разрешённое изменение оформления зафиксировано в `config/build/code-edits.json`; численные расчёты и данные графиков сравниваются с исходным эталоном. После EDA добавлены train-анализ гипотез, предобработка, восемь конфигураций классификаторов, выбор AP/F2 на validation, финальная оценка на test и пример инференса. Технический путь `./data/credit_risk_dataset.csv` переименован в `./dataset/credit_risk_dataset.csv`. Только это изменение явно нормализуется при сравнении AST. Для запуска неизменяемого старого эталона создаётся временная ссылка data → dataset в его изолированном каталоге

`tests/fixtures/solution.original.ipynb` — первоначальный эталон; `solution.working-before-layout.ipynb` — рабочий notebook непосредственно перед реорганизацией. Оба перенесены без изменения байтов. Их контрольные суммы записаны в манифесте, проверка не заменяет эталоны автоматически

Дальнейшие содержательные изменения делаются в src/. Ожидаемое отличие от эталона рассматривается осознанно; последняя успешная сборка не становится новым эталоном автоматически. Git хранит историю изменений, dist/ и tmp/ полностью исключены из Git

## Содержание завершённой работы

Все семь этапов заполнены. Общий EDA и фиксированная очистка исторически сделаны до случайного стратифицированного разбиения 70/15/15. Дополнительный анализ — только train. Pipeline обучает медианы, моду, масштабирование и кодирование только на train. Loan grade использует порядок A–G, бинарные признаки считаются номинальными. Сравниваются Dummy, логистическая регрессия, лес и гистограммный бустинг; модель выбирается по validation AP, порог — по validation F2. После фиксации test используется для итоговых метрик, bootstrap-интервалов и графиков, без донастройки.

Окончательная таблица выводов находится в этапе 7. Это учебный эксперимент на одном Kaggle-разбиении; реальные условия кредитования, внешняя валидация и мониторинг описаны как ограничения и дальнейшая работа. Сервис не развёртывается. Итоговый notebook содержит код и результаты, проектные Python-импорты для его запуска не нужны.

Описания столбцов и наши пояснения в этапе 1 хранятся в простых HTML-таблицах Markdown-ячеек. В Python остаются загрузка данных, вычисление диапазонов и определение типов признаков. При сравнении со старым эталоном исключаются только прежние словари и текстовые столбцы описаний; численные результаты и классификация признаков проверяются по-прежнему.

## Таблица выводов

В начале этапа 3 `conclusions = empty_findings()` создаёт пустую общую таблицу Pandas. После подэтапов `update_findings` добавляет записи `(id, вывод, решение)` и принимает список `remove` для закрытых записей. Постоянный id позволяет уточнить вывод без дублирования актуальной версии

`Метка` принимает `new`, `removed` или пустую строку. `findings_view(conclusions)` показывает всю таблицу, `findings_view(conclusions, only_new=True)` — только новые выводы. Новые строки выделяются зелёным и знаком «+», удаляемые — красным и знаком «−». На следующем обновлении удаляемые строки исчезают, а предыдущие новые становятся обычными. В коде метки хранятся отдельно от текста

Маленькие обновления находятся прямо после соответствующего анализа. Общие функции обработки и оформления — в соседнем `_code/findings.py`. Проверка сохранности исходного EDA отдельно сравнивает исходные данные, разбиение и матрицы до и после добавления этих служебных для анализа операций

## Пошаговое выполнение анализа

Этап 3 отдельно включает `04_hypothesis_checks.ipynb` с проверкой гипотез и `05_model_specification.ipynb` с выбором спецификаций

В этапе 4 обработка показана по шагам: состав признаков и выборки, числовые признаки, номинальные категории, грейд, общая цепочка. Короткие определения преобразований находятся прямо рядом с пояснениями в notebook. Проверка новых заявок вынесена в `_code/prepare_applications.py` и подключается перед локальным прогнозом

Проверки гипотез, обучение и итоговая оценка также разделены на пояснения и соответствующие вычисления. Крупные блоки построения диагностических графиков и итоговой таблицы выводов остаются в соседней `_code/`
