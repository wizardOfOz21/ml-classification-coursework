# Курсовая: оценка кредитного риска

Исходники определяют предметный анализ, инструменты собирают и исполняют его, тесты задают ожидаемое поведение. Готовые сборки и результаты запусков находятся в `tmp/`

## Окружение

Все команды выполняются из корня курсовой. Используйте Python 3.13+ с зависимостями из `pyproject.toml`. `requirements.lock` — точный снимок установленных версий проверенного окружения, включая транзитивные зависимости; это не универсальный кроссплатформенный lock с хешами

При создании окружения:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
source .venv/bin/activate
```

Дальше `python` означает интерпретатор этого окружения. В текущей рабочей сессии проверка также выполняется существующим окружением `../../.venv/bin/python`; переустанавливать его не требуется

## Сборка

```bash
python -m tooling.build.builder
# tmp/build/submission/solution.ipynb

python -m tooling.build.builder --target validation
# tmp/build/validation/solution.ipynb
```

Пока обе цели дают одинаковый автономный notebook; различаются назначением и путём результата. Другие форматы ещё не реализованы. `--output /путь/файл.ipynb` позволяет задать другой выход, но запрещает перезапись исходников, данных и эталонов

Манифест — `config/build/project.json`. Сборщик сохраняет Markdown, формулы, вложения и порядок операций, встраивает Python-функции на место объявленных загрузчиков. Он не выполняет вычисления, поэтому сохранённые outputs могут быть устаревшими после правок

## Интерактивная разработка

Открывайте разделы `src/notebooks/` в порядке манифеста и используйте один общий Jupyter kernel. Одинаковый интерпретатор не означает одинаковый процесс ядра

Первая служебная ячейка каждого раздела находит `config/build/project.json` и устанавливает cwd в корень курсовой. Она не попадает в сборку. Функции из `src/analysis/` загружаются в общий notebook namespace, чтобы сохранить исходные глобальные зависимости. После изменения `.py` повторно выполните ячейку загрузки. Служебные `metadata.modular` не удалять

Для запуска готового notebook нужны только Python-библиотеки и `dataset/credit_risk_dataset.csv` относительно cwd. Если открыли файл из `tmp/build/submission/`, установите cwd в корень проекта либо скопируйте notebook и dataset/ в отдельный каталог

## Проверки

```bash
python -m tooling.testing.runner                 # быстрые unit-тесты
python -m tooling.testing.runner --suite integration
python -m tooling.testing.runner --suite regression  # три чистых kernel
python -m tooling.testing.runner --suite full        # всё
```

Регрессионная проверка сама создаёт свежую сборку validation. Сначала проверяются контрольные суммы эталонов и упорядоченный AST. Затем исходник и generated исполняются в разных каталогах только с данными; модульные разделы — в общем чистом kernel. Сравниваются таблицы, итоговые объекты и данные графиков (`rtol=1e-9`, `atol=1e-11`), не случайные UUID Styler и не байты PNG

Результаты: `tmp/reports/validation_report.md`, подробности и `status.json` — в `tmp/reports/validation/`. Код выхода 0 означает успех; 1 — ошибку, расхождение или недоступность обязательной проверки. Jupyter нужны локальные порты

Исходные параметры расчётов не менялись. Технический путь `./data/credit_risk_dataset.csv` переименован в `./dataset/credit_risk_dataset.csv`. Только это изменение явно нормализуется при сравнении AST. Для запуска неизменяемого старого эталона создаётся временная ссылка data → dataset в его изолированном каталоге

## Эталоны и история

`tests/fixtures/solution.original.ipynb` — первоначальный эталон; `solution.working-before-layout.ipynb` — рабочий notebook непосредственно перед реорганизацией. Оба перенесены без изменения байтов. Их контрольные суммы записаны в манифесте, проверка не заменяет эталоны автоматически

Дальнейшие содержательные изменения делаются в src/. Ожидаемое отличие от эталона рассматривается осознанно; последняя успешная сборка не становится новым эталоном автоматически. Git хранит историю изменений, tmp/ полностью исключён из Git
